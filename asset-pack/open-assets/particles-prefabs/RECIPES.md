# Particle Prefabs — 4 Jam Essentials (3D + 2D)

> **TL;DR**: drop `JamKitParticleFactory.cs` into `Assets/Scripts/JamKit/`,
> then call `JamKitParticleFactory.CreateOneShot(...)` at hit/dust/explode/pickup moments.
> It builds a `ParticleSystem` GameObject at runtime using Kenney CC0 PNGs
> (no .prefab asset files, no GUID headaches).  Or, if you'd rather have
> real .prefab files in your project, run the baker script and it'll generate
> 8 .prefab files (4 effects × 3D/2D) into `Assets/Prefabs/JamKit/Particles/`.

## Why no .prefab files by default?

Unity `.prefab` files reference their textures by **GUID + fileID**. GUIDs are
generated by Unity on first import — you can't pre-write a .prefab that
reliably resolves outside that one-time import. Every MIT sample .prefab in
the wild ships with a sibling `.meta` (e.g. `Foo.prefab.meta` containing the
GUID), and Unity still re-imports to lock in fileIDs.

So the pragmatic, jam-proof option is: build the ParticleSystem GameObject at
runtime from a C# factory. You still get:

- Reusable particle configs (4 named effects, each tuned)
- Object-poolable (combine with `scripts/ObjectPool.cs`)
- Referenceable (assign the returned `ParticleSystem` to your JuiceManager)
- Zero import-time failure modes

## Want real .prefab files? Use the baker script

If your workflow demands drag-and-drop prefabs (e.g. handing a designer's
inspector a prefab to tweak), drop the **`Editor/JamKitParticlePrefabBaker.cs`**
script into your project's `Assets/Editor/` folder. Then in Unity:

```
Tools → JamKit → Bake Particle Prefabs (3D + 2D)
```

This bakes **8 .prefab files** into `Assets/Prefabs/JamKit/Particles/`:

| File | Effect | Variant |
| --- | --- | --- |
| `Sparks3D.prefab` | Hit sparks | 3D (gravity 0.6, world-space) |
| `Sparks2D.prefab` | Hit sparks | 2D (gravity 0.2, smaller size) |
| `LandingDust3D.prefab` | Landing dust | 3D |
| `LandingDust2D.prefab` | Landing dust | 2D |
| `Explosion3D.prefab` | Death explosion | 3D |
| `Explosion2D.prefab` | Death explosion | 2D |
| `PickupGlow3D.prefab` | Collectible glow | 3D |
| `PickupGlow2D.prefab` | Collectible glow | 2D |

Each .prefab is a real `ParticleSystem` GameObject with the shader/material
already wired (URP `Particles/Unlit` or Built-in `Particles/Standard Unlit`
based on your project's active render pipeline). GUID + .meta are auto-minted
by `PrefabUtility.SaveAsPrefabAsset()` at save time, so they import cleanly.

> **Why bake instead of hand-write?** A hand-written .prefab has GUID
> baked into its references; if those references break (missing texture, GUID
> collision on import), the prefab renders magenta. The baker creates the
> GameObject *in memory* via `Create()`, then asks Unity to save it as a
> proper prefab with fresh GUIDs.

The baker menu also has sub-items for each individual effect:

```
Tools → JamKit → Bake Particle Prefabs →
  ├─ Sparks (3D + 2D)
  ├─ Dust (3D + 2D)
  ├─ Explosion (3D + 2D)
  └─ Pickup Glow (3D + 2D)
```

## The 4 effects (tuning table)

| Effect            | Kenney PNG       | Tint                       | Burst | Lifetime | Speed | Size | Notes |
| ----------------- | ---------------- | -------------------------- | -----:| --------:| -----:| ----:| ----- |
| **Hit sparks**    | `muzzle_01.png`  | `(1.0, 0.85, 0.4)` warm    |    16 |   0.4 s  |    4  | 0.4  | Cone, additive-friendly |
| **Landing dust**  | `dirt_01.png`    | `(0.65, 0.55, 0.45)` brown |    16 |   0.4 s  |    4  | 0.4  | Cone, gravity 0.6 |
| **Death explosion** | `magic_03.png`  | `(1.0, 0.5, 0.2)` fire     |    16 |   0.4 s  |    4  | 0.4  | Cone, slightly more size in inspector |
| **Collectible glow** | `flare_01.png` | `(1.0, 0.9, 0.3)` gold     |    16 |   0.4 s  |    4  | 0.4  | Soft, no gravity, looping |

For the collectible glow, set `main.loop = true` and `main.startSpeed = 0` in
the inspector after instantiating (or fork the helper).

## Dual-render-pipeline support (URP + Built-in)

The factory auto-detects which render pipeline is active at runtime via
`UnityEngine.Rendering.GraphicsSettings.currentRenderPipeline`:

- **URP / SRP active** → uses `Universal Render Pipeline/Particles/Unlit`
  shader, properties `_BaseColor` (Color) + `_BaseMap` (Texture).
  Additive blending via `_Surface = 1` (Transparent) + `_Blend = 2` (Additive).
- **Built-in Render Pipeline** → falls back to `Particles/Standard Unlit`,
  properties `_MainTex` + `_TintColor` + `_Mode`.
  Additive blending via `_Mode = 3` (Transparent) + `_SrcBlend = _DstBlend = One`.

You can query the active pipeline at runtime with
`JamKitParticleFactory.IsUsingURP` (returns `true` if URP, `false` if Built-in).
The same .dll works in either pipeline without recompiling.

**Why this matters**: hard-coding the Built-in particle shader in a URP
project produces magenta "shader missing" errors (the Built-in shader isn't
shipped when URP is the active pipeline). Same issue in reverse. The dual
path means your jam project works on day 1 whether you start with URP
template or Built-in template.

## Usage from your existing JuiceManager

```csharp
// scripts/JuiceManager.cs extension
using JamKit;

public void HitSpark(Vector3 pos) {
    JamKitParticleFactory.CreateOneShot(transform, JamKitParticleFactory.KenneyTex.Muzzle01)
        .transform.position = pos;
}

public void LandingDust(Vector3 pos) {
    JamKitParticleFactory.CreateOneShot(transform, JamKitParticleFactory.KenneyTex.Dirt01)
        .transform.position = pos;
}

public void Explode(Vector3 pos) {
    JamKitParticleFactory.CreateOneShot(transform, JamKitParticleFactory.KenneyTex.Magic03)
        .transform.position = pos;
}

public void CollectibleGlow(Vector3 pos) {
    var ps = JamKitParticleFactory.Create(transform, JamKitParticleFactory.KenneyTex.Flare01);
    var main = ps.main;
    main.loop = true;
    main.startSpeed = 0;
    ps.transform.position = pos;
}
```

### Using the baked prefabs (if you ran the baker)

```csharp
using JamKit;
using UnityEngine;

public class JuiceManager : MonoBehaviour {
    [SerializeField] private GameObject sparks3DPrefab;
    [SerializeField] private GameObject sparks2DPrefab;
    [SerializeField] private GameObject explosion3DPrefab;

    public void HitSpark(Vector3 pos) {
        var ps = Instantiate(sparks3DPrefab, pos, Quaternion.identity).GetComponent<ParticleSystem>();
        ps.Emit(16);
        Destroy(ps.gameObject, 1.5f);
    }

    public void Explode(Vector3 pos) {
        Instantiate(explosion3DPrefab, pos, Quaternion.identity);
        // prefab already has PlayOnAwake=true + duration ~1.5s, self-cleaning
        // via the ParticleSystemStopAction in main module (auto-destroy).
    }
}
```

## Reference .prefab (MIT)

`_MIT_reference_SuccessParticles.prefab` is the unmodified Unity ParticleSystem
prefab from `CompleteUnityDeveloper2/3_Project_Boost` (MIT, GameDev.tv / EmbraceIT).
It's 77KB of well-structured YAML that shows every module + every curve — use
it as a **copy-paste template** in the Unity editor if you want hand-crafted
.prefab files (right-click → Copy → Paste in your Assets folder, then tweak
in inspector).

## Kenney texture import settings (set these once in inspector)

For each of the 4 PNGs:

- **Texture Type**: `Default` (not `Sprite` — we use the ParticleSystemRenderer)
- **Alpha Is Transparency**: ✓
- **Wrap Mode**: `Clamp`
- **Filter Mode**: `Bilinear`
- **Max Size**: 256 (these are tiny circles, no need for 2048)

If you prefer `Sprite (2D and UI)` textures, use `Sprite` instead of `Default`
and set the ParticleSystemRenderer `Sprite` mode + assign the sprite.

## Runtime fallback

The factory uses `#if UNITY_EDITOR` to load textures by asset path so dev
works out of the box. For builds, drop the 4 PNGs into
`Assets/Resources/Particles/` (filenames: `muzzle_01`, `dirt_01`, `magic_03`,
`flare_01` — without extension) and the `Resources.Load` branch will pick
them up automatically.
